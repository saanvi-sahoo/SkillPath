# Skill gap analysis and the 30-day roadmap

Implements project doc §10 (skill normalisation, categorisation, comparison) and §11 (a personalised 30-day roadmap).

## 1. Skill normalisation and exact comparison (`src/skills/normalizer.py`)

```
LLM-extracted strings ──► normalize() ──► categorize() ──► compare(candidate, required)
"Tools: power-bi"          "Power BI"      "Data Analysis & BI"   matched / gaps / related / implied
```

| Function | Behaviour |
|---|---|
| `normalize(s)` | Strips `brain.py` prefixes ("Tools:", "Soft Skills:"…), lowercases, and maps about 120 aliases to canonical names (`k8s`→Kubernetes, `powerbi`→Power BI). Unknown skills are kept, title-cased |
| `categorize(s)` | Rule map with 10 categories (Programming, Databases, AI/ML, Data Analysis & BI, Data Engineering, Cloud/DevOps, Web & Backend, Tools, Soft Skills, Project Management). Anything unknown is `Other`, never guessed |
| `compare(c, r)` | **Exact canonical match.** A required skill counts as matched only if the candidate has it, or has a skill that *proves* it (`IMPLIES`, e.g. MySQL ⇒ SQL, Spring Boot ⇒ Java) |

**Related ≠ equivalent (doc §10):** `RELATED` groups (Docker~Kubernetes, AWS~Azure~GCP, Power BI~Tableau…) only produce a `related_background` note. The requirement stays a gap.

```python
compare(["Python", "Docker", "MySQL", "Excel"], ["python", "Kubernetes", "SQL", "Tools: Power BI", "Docker"])
# matched: Python, Docker, SQL (SQL via MySQL)   gaps: Kubernetes, Power BI
# related_background: {"Kubernetes": ["Docker"]}  match_ratio: 0.6
```
API: `POST /skills/compare {"candidate_skills": [...], "required_skills": [...]}`.

## 2. 30-day roadmap (`src/roadmap/generator.py`)

| Step | What happens | Why |
|---|---|---|
| 1. Gaps | `compare()` on candidate vs required skills (or the given gaps) | Auditable exact gap list, not the LLM's own list |
| 2. Prioritise | **Prerequisites first** (`PREREQS`: Python→ML, Docker→Kubernetes, SQL→Spark…), then **market importance**: the share of the target role's top-25 career records (the source-of-truth dataset, via `retrieve_careers`) that list the skill | "Prioritise by importance and prerequisites, not just LLM ordering" (doc §11.2) |
| 3. Skeleton | Fixed in code. Review days 7/14/21/28, capstone project on days 29–30, 24 learning days split by weight (at least 2 per gap, at most 8 gaps; the rest are *deferred*) | Realistic allocation with review time reserved |
| 4. Fill | LLM (prompt `roadmap_v1`, `gpt-oss-120b`, pydantic schema `Roadmap`) writes topic, prerequisite, learning task, practice task, minutes and completion criterion for each day | Specific, checkable daily work |
| 5. Validate + repair | Exactly 30 days, numbered 1–30, skill and kind unchanged, minutes ≤ budget × 1.1, no empty fields, every scheduled gap covered. Problems are repaired from templates and listed in `validation.issues` | The LLM never has the last word on structure |
| 6. Resources | Links from the latest profile analysis (Tavily resources) are attached where skills match | Reuses vetted links |
| Fallback | If the LLM is unavailable, every day uses the deterministic template | It always returns a plan |

Day schema (doc §11.1):
```json
{"day": 1, "skill": "Data Visualization", "kind": "learn", "topic": "Chart Selection Principles",
 "prerequisite": "none", "learning_task": "...", "practice_task": "Classify 10 analytical scenarios into the correct chart type",
 "estimated_minutes": 60, "completion_criteria": "10 out of 10 chart choices correctly identified", "resources": []}
```

**Run:** `python -m src.roadmap.generator --from-profile --minutes 90` · `POST /roadmap {"from_profile": true, "daily_minutes": 90}` · Streamlit **Learning Paths** tab → *Generate 30-day roadmap*.

**First measured run (2026-11-08, data-analyst test profile, 90 min/day):**
- Gaps were ordered Data Visualization (0.32 market share) → Tableau (0.24) → Statistics (0.24) → Communication (0.00), getting 7 / 6 / 6 / 5 days.
- `valid: true`: 30 days, all gaps covered, max 90 minutes, 0 repairs.
- Generated by the LLM in about 42 s (one structured call).
- Saved in `reports/roadmaps/`.

## 3. Limitations
- Soft skills (e.g. Communication) score 0 market importance because the dataset rarely lists them. They still get the minimum days.
- `IMPLIES`, `RELATED` and `PREREQS` are hand-written and small. Extend them with care, and review changes as a team.
- An LLM fallback for categorising unknown skills (doc §10) isn't implemented yet. Unknown skills show as `Other`.
- Progress tracking and regenerating the remaining days (doc §11.2 step 36) are still to do.

## 4. Roadmap specificity (E33–E35)
| Improvement | Before | After |
|---|---|---|
| Daily topics | "SQL - part 1/2/3" placeholders, or a 216 s Mistral JSON | Curriculum per skill (`src/roadmap/syllabus.py`, ~25 skills): ordered topics with a learning task, a hands-on task and a checkable completion criterion; then a mini project and interview readiness |
| Resources | Only when the profile analysis found links (needs Tavily) | Curated **free official resources** for every learning day of a known skill (SQLBolt, Python tutorial, Microsoft Learn Power BI, Tableau training, Khan Academy, Google ML Crash Course, Docker/Kubernetes docs, AWS Skill Builder, Spring guides, …) |
| Capstone (days 29–30) | Generic "mini project" | **Role-specific:** analyst → end-to-end dashboard with 3 recommendations; backend → REST service, tests, container, CI/CD deploy; ML → model trained and served via API; cloud/DevOps → IaC + pipeline. Each names the person's gap skills. Day 29 = plan & build, day 30 = README, resume line, 2-minute walkthrough |
| Speed | 216 s locally | < 1 s (template); AI-written plans ≤ 75 s with fallback |

**Evaluation** (`python -m src.eval.roadmap_eval`, 3 personas, deterministic): valid 30 days, every gap covered, prerequisites before dependants, within the time budget, resources on every known-skill day, role-specific capstone, no generic topics → **3/3 personas pass all 7 checks** (`reports/roadmaps/roadmap_eval_*.json`).

- In the chat, "make me a 30-day … plan" runs this generator first (time budget from "45 minutes daily", known skills
  from "I know Python…", starter skills when only a role is named) and gives the plan to the model as a source.

## 6. Adaptive roadmap (E38, review 3 §5)
A valid plan is not necessarily a useful one: students miss days, find a topic hard, already know part of it, or change
goals. `src/roadmap/adapt.py` tracks a status per day (`not_started`, `completed`, `needs_revision`, `skipped`,
`already_known`) and `adapt_roadmap(roadmap, progress, today)` rebalances only the remaining days:

- completed days stay as history; a hard day gets an easier **revision day** immediately (smaller steps, simpler practice, then the original task);
- missed days move forward in order; already-known days are removed and later topics move up;
- if the work no longer fits in 30 days, weekly reviews are dropped first, then the lowest-priority learning days are **deferred** (listed, never silently lost); the capstone stays last;
- the daily minute budget never changes.

The roadmap page has a *Track progress and adapt the plan* panel (status per day, "Which day are you on?", *Rebalance my
plan*). It shows the **task completion rate** (completed / days due, the review's real-world metric) and saves a progress
summary to the student's profile, so the advisor can answer "how am I doing?" from it. In chat, "I missed 3 days" or "DAX
is too hard" triggers the same adapt-don't-repeat rule, and a plan asked for after "the second one" / "one hour daily" uses
the selected career, the minutes and the skills the student said they lack (conversation state, docs/chatbot.md).
Tests: `tests/test_e38.py::test_adaptive_roadmap`.
